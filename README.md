# Асинхронный процессинг платежей

FastAPI принимает платёж, PostgreSQL хранит его состояние, а RabbitMQ доставляет событие обработчику на FastStream. Обработчик эмулирует шлюз с задержкой 2–5 секунд и вероятностью успеха 90%. По завершении он отправляет webhook.

## Запуск

Требуются Docker и Docker Compose v2.

```sh
cp .env.example .env
docker compose up --build -d
docker compose ps
docker compose logs -f consumer
```

API доступен по адресу `http://localhost:8000`. Интерфейс RabbitMQ доступен по адресу `http://localhost:15672` с локальными учётными данными `payments` / `payments`. Порты можно изменить в `.env`. API выполняет `alembic upgrade head` при запуске. PostgreSQL и RabbitMQ используют именованные тома.

## API

Оба эндпоинта требуют `X-API-Key` со значением `API_KEY` из `.env`. Примеры используют ключ из `.env.example`.

### Создание платежа

Подставьте URL webhook, доступный из контейнера `consumer`. Для автоматической проверки можно использовать локальный приёмник из раздела «Проверка».

```sh
WEBHOOK_URL='https://example.com/webhooks/payments'

curl -i http://localhost:8000/api/v1/payments \
  -H 'X-API-Key: local-demo-key' \
  -H 'Idempotency-Key: order-42' \
  -H 'Content-Type: application/json' \
  --data "{\"amount\":\"125.50\",\"currency\":\"RUB\",\"description\":\"Оплата заказа 42\",\"metadata\":{\"order_id\":42},\"webhook_url\":\"$WEBHOOK_URL\"}"
```

Пример ответа `202 Accepted`:

```json
{
  "payment_id": "66fd2982-b6d8-42b1-927b-ff47fb25f7e4",
  "status": "pending",
  "created_at": "2026-11-06T12:00:00Z"
}
```

Сумма положительная, до 16 цифр в целой части и до двух знаков после запятой. API принимает JSON-число или десятичную строку и возвращает сумму строкой без потери точности. Валюты: `RUB`, `USD`, `EUR`. `metadata` — JSON-объект, по умолчанию `{}`.

При повторе запроса с тем же `Idempotency-Key` и теми же данными API возвращает `202`, исходный ID, время создания и текущий статус платежа. Если ключ уже использован для других данных, API отвечает `409 Conflict`. Ключ — от 1 до 255 печатных ASCII-символов без пробелов. Ошибки валидации возвращают `422`, отсутствующий или неверный API-ключ — `401`.

### Получение платежа

```sh
curl -i http://localhost:8000/api/v1/payments/66fd2982-b6d8-42b1-927b-ff47fb25f7e4 \
  -H 'X-API-Key: local-demo-key'
```

Подставьте `payment_id` из ответа на создание. GET возвращает `200` с данными платежа и `processed_at`. Пока платёж в статусе `pending`, `processed_at` равен `null`. Для неизвестного ID возвращается `404`.

## Доставка и повторные попытки

1. API сохраняет платёж и событие в таблице `outbox` одной транзакцией. Ограничение `UNIQUE` защищает от гонки между запросами с одним ключом.
2. Фоновая задача в процессе `consumer` читает неопубликованные строки через `FOR UPDATE SKIP LOCKED`. Она отправляет persistent-сообщение через exchange `payments` в quorum-очередь `payments.new`. `published_at` записывается после положительного publisher confirm. Если брокер недоступен или не может маршрутизировать сообщение, строка остаётся в outbox до следующей попытки.
3. Единственный обработчик фиксирует результат шлюза в БД перед отправкой webhook. Повторное сообщение пропускает шлюз, если результат уже зафиксирован, и пропускает webhook, если его доставка сохранена.
4. Webhook отправляется методом POST. Любой ответ `2xx` подтверждает доставку. Для таймаута, сетевой ошибки или HTTP-ответа вне `2xx` выполняется до трёх попыток всего. Паузы перед второй и третьей попытками составляют 1 и 2 секунды. Счётчик ошибок и время следующей попытки сохраняются в БД. Одна попытка HTTP ограничена пятью секундами.
5. После успешной доставки consumer подтверждает сообщение. После исчерпания попыток он отклоняет сообщение, и RabbitMQ направляет его через `payments.dlx` в `payments.dlq`. Некорректные события и неизвестные пары ID события и платежа отправляются в DLQ сразу. Если шлюз вернул `failed`, это результат платежа и повод отправить webhook.

Тело webhook:

```json
{
  "event_id": "c225a37d-f351-4c37-a363-a5cf1b794c57",
  "payment_id": "66fd2982-b6d8-42b1-927b-ff47fb25f7e4",
  "status": "succeeded",
  "amount": "125.50",
  "currency": "RUB",
  "processed_at": "2026-11-06T12:00:04Z"
}
```

Публикация и уведомления работают по принципу **at least once**. Например, сбой после ответа webhook, но до записи о доставке, может привести к повторному POST. Получатель может дедуплицировать уведомления по `event_id`, который также передаётся в заголовке `Idempotency-Key`.

Конфигурация Compose предназначена для локального запуска с доверенными клиентами и webhook URL. Приёмник может находиться во внутренней Docker-сети. Consumer следует указанному URL без HTTP-редиректов.

## Проверка

На запущенном Compose-стеке команда ниже поднимает временный HTTP-приёмник в той же сети. Она проверяет авторизацию, конкурентную идемпотентность, успешную доставку с третьей попытки, интервалы между повторами, обработку дубликата события и перевод в DLQ.

```sh
docker compose run --rm --no-deps --name payments-smoke \
  -v "$PWD/tests:/checks:ro" api python /checks/smoke.py
```

Проверить синхронность моделей и миграции:

```sh
docker compose exec api alembic check
```

Остановить сервисы и сохранить данные: `docker compose down`.
